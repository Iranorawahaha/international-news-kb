## 系统概述

### 什么是"国际新闻看板"?

**国际新闻看板**是一个高质量国际新闻自动采集、筛选、呈现和分享平台。它能够：

- ✅ **自动采集**来自30个权威信源的国际新闻（中英文媒体+政府机构）
- ✅ **智能筛选**重点关注：中美关系、经贸制裁、AI竞争、外交资讯
- ✅ **专业呈现**通过GitHub Pages以网页形式展示，支持搜索/筛选/排序
- ✅ **一键分享**生成可公开访问的URL，方便与同事共享
- ✅ **手动更新**由用户控制更新时机，确保数据时效性

### 适用场景

| 场景 | 说明 |
|------|------|
| **个人每日新闻阅读** | 每天早晚各更新一次，获取全球重要新闻 |
| **团队信息共享** | 将页面链接分享给同事，统一信息来源 |
| **国际环境洞察** | 跟踪中美关系、AI竞争、地缘政治等关键议题 |
| **资料归档研究** | 历史数据保存在本地，可随时回溯 |

### 2. 单文件自包含HTML网页

**特点**：
- 所有CSS样式、JavaScript逻辑、新闻数据全部内嵌在一个HTML文件中
- 无外部依赖，解决了路径导致的404问题
- 支持响应式设计（电脑/手机/平板自适应）
- 文件大小约30-35KB（25-30条新闻）

**功能清单**：
- ✅ 9列数据表格展示（#、日期、标题、摘要、来源、分类、重要性、关键词、原文链接）
- ✅ 实时搜索（支持标题、摘要、关键词模糊匹配）
- ✅ 多维度筛选（来源、分类、重要性）
- ✅ 可点击的原文链接按钮（紫色渐变，新标签页打开）
- ✅ 统计卡片（总数、信源数、分类数、高重要性数）
- ✅ 悬停动画效果

### 3. 一键更新脚本

```bash
./update-news.sh
```

**自动化流程**：
1. 基础采集（中文信源）
2. WebFetch补充提示（交互式确认）
3. 数据质量验证（统计+URL检查）
4. 单文件HTML生成
5. Git提交并推送到GitHub Pages

**耗时**：3-5分钟（含WebFetch）或30-60秒（仅基础采集）

### 4. URL完整性保障机制 ⭐V1.0核心特性

**4道防线防止URL缺失**：

| 防线 | 机制 | 位置 |
|------|------|------|
| 第1道 | WebFetch Prompt强制要求返回完整URL | `fetch_news_v3.py` 第85-114行 |
| 第2道 | `validate_urls()` 自动验证覆盖率 | `fetch_news_v3.py` validate_urls方法 |
| 第3道 | HTML生成器正确渲染第9列"原文链接" | `update-news.sh` 第4步Python代码 |
| 第4道 | 质量标准要求URL覆盖率≥95% | `DAILY-UPDATE-MANUAL.md` 检查清单 |

**效果**：从根本上杜绝了"新闻缺少原文链接"的问题

### 关键设计决策

#### 为什么选择单文件HTML？

**问题**：初始版本采用多文件结构（css/style.css、js/app.js、index.html），部署到GitHub Pages后出现404错误。

**解决方案**：将所有CSS、JavaScript、数据内嵌到一个HTML文件中。

**优点**：
- ✅ 无路径依赖问题
- ✅ 部署简单（只需上传1个文件）
- ✅ 加载速度快（减少HTTP请求）
- ✅ 方便备份和迁移

**缺点**：
- ❌ 文件较大（30-35KB vs 多文件总计15KB）
- ❌ 不利于代码复用（但本场景不需要）

**结论**：对于静态展示型页面，单文件架构是最佳选择。

#### 为什么需要手动更新而非全自动？

**原因**：
1. **WebFetch步骤需要在WorkBuddy环境中执行**，无法完全自动化
2. **用户希望控制更新时机**（每日2次：9:30早间 + 17:00下午）
3. **确保数据质量**：人工确认可以避免抓取到低质量内容
4. **灵活性**：可以根据当天情况决定是否补充英文信源

**未来可能的改进**：
- 设置macOS LaunchAgent定时提醒用户执行更新
- 开发WorkBuddy Automation实现半自动更新

## 遇到的问题及解决方案

### 问题1：GitHub Pages页面显示混乱（2026-07-30）

**现象**：
- 页面CSS/JS加载失败（404错误）
- 显示原始HTML代码而非渲染后的页面
- 表格无样式，布局混乱

**根本原因**：
- 初始版本采用多文件结构（`css/style.css`, `js/*.js`）
- 但实际文件放在根目录，而HTML引用的是子目录路径
- 导致路径不匹配，浏览器无法加载资源

**解决方案**：
✅ **重构为单文件自包含HTML**
- 将所有CSS样式（~200行）内嵌到`<style>`标签
- 将所有JavaScript逻辑（~150行）内嵌到`<script>`标签
- 将JSON数据直接嵌入JS变量`const NEWS_DATA = [...]`
- 消除所有外部文件依赖

**经验教训**：
- 静态网站部署前必须测试路径正确性
- 单文件架构对于简单展示型页面更可靠
- GitHub Pages对路径大小写敏感

### 问题2：Git推送代理失败（多次发生）

**现象**：
```
fatal: unable to access 'https://github.com/...': 
Failed to connect to 127.0.0.1 port 49433: CONNECT tunnel failed, response 502
```

**根本原因**：
- 用户使用代理软件（Clash/V2Ray）访问GitHub
- 代理端口动态变化（49433 → 7890）
- Git配置中的代理端口过期

**解决方案**：
```bash
# 1. 检查当前代理端口
echo $https_proxy
# 输出: http://127.0.0.1:7890

# 2. 更新Git配置
git config http.proxy http://127.0.0.1:7890
git config https.proxy http://127.0.0.1:7890

# 3. 重新推送
git push origin main
```

**预防措施**：
- 在`update-news.sh`开头添加自动检测代理端口的逻辑
- 推送失败时自动提示用户检查代理设置

#### 重要性评估算法

```python
def assess_importance(text):
    high_keywords = ['中美', '特朗普', '制裁', '战争', '导弹', 'AI禁令', '重大', '紧急']
    medium_keywords = ['会议', '谈判', '协议', '合作', '声明']

    if any(kw in text for kw in high_keywords):
        return '高'
    elif any(kw in text for kw in medium_keywords):
        return '中'
    else:
        return '低'
```

#### 去重机制

- **基于标题相似度**：去除标点符号后比对
- **阈值**：完全相同或高度相似（>90%重复）
- **保留策略**：优先保留WebFetch获取的版本（质量更高）
